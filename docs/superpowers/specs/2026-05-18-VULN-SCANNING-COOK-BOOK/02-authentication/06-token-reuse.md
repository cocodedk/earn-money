## Purpose

Detect password reset tokens that remain valid after successful use. A reusable reset token lets anyone with the token change the account password more than once, which increases the impact of leaked reset links, mailbox compromise, browser history exposure, proxy logs, and shared-device access.

## Inputs

The runner receives a shared `ScanTarget` plus reset-flow configuration.

Required inputs:

* `target`: shared `ScanTarget`.
* `reset_request_url`: URL or route hint for the password reset request form/API.
* `reset_complete_url`: optional route hint for the token consumption form/API.
* `test_account`: an owned account approved for password-reset testing.
* `test_account_email`: email address for the owned account.
* `mailbox_source`: approved source for retrieving reset links for the owned account. This may be a fixture mailbox, test mail API, captured container log, or explicit test hook.
* `password_a`: known starting password for the owned account.
* `password_b`: first replacement password generated by the runner.
* `password_c`: second replacement password generated by the runner for replay testing.

Optional inputs:

* `login_url`: login endpoint used to verify which password is active after each reset.
* `csrf_handling`: setting for extracting and replaying CSRF tokens from forms.
* `token_param_names`: optional list of likely token parameter names, such as `token`, `resetToken`, `key`, `code`.
* `max_reset_emails_to_inspect`: default `3`.
* `max_token_replay_attempts`: default `1`.
* `request_timeout_ms`: default from shared runner settings.
* `restore_original_password`: default `true` for fixtures and controlled targets.
* `allow_mutation`: must be `true`; otherwise this check returns `rejected`.

The runner must not run this check against real user accounts. It needs an owned account because a successful test changes the account password.

## Detection logic

This check is deterministic and stateful. It runs only when mutation is explicitly allowed.

### Flow

1. Validate that `test_account_email`, `password_a`, `password_b`, `password_c`, and `mailbox_source` are present.
2. Submit a reset request for `test_account_email`.
3. Retrieve the newest reset email or reset-link record from `mailbox_source`.
4. Extract the reset token and reset URL.
5. Submit the reset completion request once with `password_b`.
6. Verify that `password_b` works.
7. Replay the same reset token once with `password_c`.
8. Verify whether the replay changed the password to `password_c`.
9. If configured, restore the account to `password_a` or a fresh known password.
10. Persist evidence for the original token use, replay attempt, and login verification result.

### Token extraction

The runner may extract tokens from:

* link query parameters
* path segments
* form action URLs
* JSON reset records in fixtures
* test mail API fields

The runner must not infer vulnerability from token shape alone. Token length, encoding, UUID format, JWT format, or timestamp-like contents are not findings by themselves.

### Request handling

For HTML flows:

* Fetch the reset completion page using the token URL.
* Extract form action, method, hidden fields, and CSRF token.
* Submit new password fields using detected field names.
* Preserve cookies set by the reset page only for the same flow.

For JSON/API flows:

* Submit the reset request using the detected content type.
* Use the API response or mailbox link to locate the token.
* Submit the reset completion request with the same token and `password_b`.
* Replay the same request shape with `password_c`.

The replay must use the same token value. It may refresh CSRF tokens if the application requires a new CSRF token for form submission, but it must not request a new password reset token between first use and replay.

### Classification

Confirmed finding:

* First token use succeeds and changes the owned account password to `password_b`.
* Replaying the same token succeeds and changes the owned account password to `password_c`.

Rejected finding:

* First token use succeeds.
* Replaying the same token is rejected, expired, invalid, or does not change the password.

Candidate finding:

* Replay receives a success-like response, but login verification is unavailable or inconclusive.

Stale finding:

* Evidence was collected before a later successful mitigation check, or the target flow changed and the stored token route no longer matches current behavior.

### Evidence to collect

Collect shared `Evidence` records for:

* reset request submission
* reset email or reset-link retrieval metadata
* token extraction source, with token value redacted
* first token consumption response
* login verification after first consumption
* replay token consumption response
* login verification after replay
* optional restore-password response

Redact reset tokens in stored evidence. Keep a stable hash of the token for correlation.

Suggested redaction:

```text
reset_token_redacted = "<redacted:sha256:12chars>"
```

Do not store full reset links if they contain live tokens. Store the URL origin, path, parameter names, and redacted token hash.

## Persistence

Use shared `ScanTarget` and `Evidence` from `../00-shared-schema.md`. Do not redefine them here.

Define only the stub-specific signature and finding types.

```python
from typing import Literal, TypedDict

Confidence = Literal["low", "medium", "high"]
FindingStatus = Literal["candidate", "confirmed", "rejected", "stale"]

class TokenReuseSignature(TypedDict, total=False):
    reset_request_url: str
    reset_complete_url: str
    token_location: Literal["query", "path", "form", "json", "mailbox_record", "unknown"]
    token_param_name: str
    token_hash: str
    first_use_status_code: int
    replay_status_code: int
    first_login_verified: bool
    replay_login_verified: bool
    replay_changed_password: bool
    csrf_refreshed_for_replay: bool
    reset_requested_again_between_use_and_replay: bool
    response_similarity_score: float
    replay_rejection_reason: str

class TokenReuseFinding(TypedDict):
    target: "ScanTarget"
    status: FindingStatus
    confidence: Confidence
    signature: TokenReuseSignature
    evidence: list["Evidence"]
    summary: str
    impact: str
    remediation: str
```

Persistence rules:

* Store one `TokenReuseFinding` per tested reset flow and account.
* Link every finding to the exact evidence IDs used for classification.
* Store token hashes only. Never store raw reset tokens.
* Store whether login verification proved the password changed after replay.
* Store `reset_requested_again_between_use_and_replay=false` for confirmed findings.
* Store rejected findings when the flow was testable and replay was blocked, because this is useful regression evidence.
* Mark old confirmed findings as `stale` when a later run proves single-use behavior on the same reset flow.

## Safety

This is a mutating check. It changes the password of an owned test account.

Safety requirements:

* Run only when `allow_mutation=true`.
* Run only against an owned test account provided for scanning.
* Do not run against real users, guessed users, harvested emails, admin accounts, or production customer accounts.
* Do not request password resets for accounts not explicitly provided in the scan configuration.
* Do not brute force tokens.
* Do not guess token values.
* Do not enumerate users.
* Do not perform more than one replay attempt per token unless a fixture-specific test explicitly allows it.
* Do not request a second reset token between first use and replay.
* Do not send reset tokens to external services.
* Do not store raw reset tokens, full reset links, mailbox contents, or passwords in evidence.
* Restore the original password when configured and safe to do so.
* If restore fails, mark the run as requiring operator attention and include only redacted evidence.

HTTP-method discipline:

* Use `GET` only to fetch forms and reset pages.
* Use the form or API-declared method for reset request and reset completion.
* Do not mutate unrelated account settings.
* Do not follow off-site reset links unless the target scope explicitly includes that host.
* Do not submit destructive actions found in page content.

Payload restrictions:

* Use generated scanner passwords that meet the target’s password policy.
* Do not include shell metacharacter payloads, SQL payloads, XSS payloads, or command payloads.
* Do not use leaked password lists.
* Do not reuse real user passwords.

PII handling:

* Treat email addresses, reset links, tokens, cookies, and mailbox content as sensitive.
* Redact tokens, cookies, and passwords before logging or persistence.
* Store only the minimum reset email metadata needed to prove the flow.

AI involvement: `None`.

Deterministic gap:

* If the runner cannot determine whether replay changed the password because login verification is unavailable, it may store a `candidate` finding based only on response evidence.
* AI must not be used to decide exploitability, token validity, or account state.

## Pass/fail check

The implementation passes when all assertions below are true.

### Positive assertions

* The runner refuses to run unless `allow_mutation=true`.
* The runner refuses to run without an owned `test_account_email`.
* The runner requests exactly one reset token for the test account before replay.
* The runner extracts the token from the approved mailbox or fixture source.
* The runner consumes the token once with `password_b`.
* The runner verifies that `password_b` works when `login_url` is configured.
* The runner reuses the same token once with `password_c`.
* The runner reports `confirmed` with `high` confidence when replay changes the password to `password_c`.
* The runner reports `rejected` when replay fails and `password_b` remains active.
* The runner reports `candidate` when replay appears accepted but password-state verification is unavailable.
* The runner stores evidence IDs for first use, replay, and login verification.
* The runner redacts reset tokens, reset links, cookies, and passwords from logs and evidence.
* The runner records a stable token hash for correlation.
* The runner restores the account password when `restore_original_password=true` and restore is possible.

### Negative assertions

* The runner must not test accounts outside the provided owned test account.
* The runner must not guess or brute force reset tokens.
* The runner must not use leaked password lists.
* The runner must not retry many token variants.
* The runner must not request a new reset token between first use and replay.
* The runner must not classify a finding as `confirmed` from HTTP 200 alone.
* The runner must not store raw reset tokens.
* The runner must not store raw passwords.
* The runner must not follow out-of-scope reset links.
* The runner must not use AI to classify the result.
* The runner must not hard-code expected behavior based on hostname, product name, or fixture name.
* The runner must not leave the test account in an unknown password state without reporting operator attention.

## Test fixtures

Preferred fixture: `webgoat`.

Use WebGoat’s password reset lesson if the container exposes a reusable-token scenario suitable for deterministic testing. The fixture should provide:

* a controlled user account
* a reset request endpoint
* a reset completion endpoint
* a way to retrieve the reset link or token from the test environment
* login verification after password change

Alternative fixture: `juice-shop`.

Use only if the container exposes a password reset flow where the reset token can be captured through a safe test mailbox, logs, or fixture hook.

If neither existing fixture gives deterministic token retrieval, create a small fixture named `password-reset-token-reuse`.

Fixture requirements for `password-reset-token-reuse`:

* `POST /forgot-password` accepts an owned test email.
* The app writes reset links to a fixture mailbox API or local test log.
* `GET /reset-password?token=...` serves a reset form.
* `POST /reset-password` accepts `token`, `password`, and `password_confirm`.
* Vulnerable mode allows the same token to be used twice.
* Fixed mode invalidates the token after first successful use.
* `POST /login` verifies the current password.
* Fixture exposes a reset/seed endpoint available only inside the test network.

Required fixture cases:

* vulnerable reusable token
* fixed single-use token
* expired token
* invalid token
* replay returns success-like page but does not change password
* CSRF token required on reset form
* token in path segment instead of query parameter
* JSON API reset flow
* restore-password failure case
