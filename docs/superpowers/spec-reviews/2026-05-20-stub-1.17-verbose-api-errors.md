## Verdict

Stub 1.17 is **functionally end-to-end** for the spec's MVP slice (baseline + nonexistent-API-sibling probe, three strong-indicator families, JSON debug fields with .NET PascalCase coverage). The 5 already-tracked PR #24 deferrals correctly capture the next slice of probe work.

The audit surfaced **two material gaps** beyond what PR #24 tracks:

1. **`Evidence.raw_excerpt` is a synthetic descriptor, not a redacted body slice.** Spec §Persistence wants the body excerpt for downstream review. Today's value `"<probe_kind>: <url> (status N)"` is operationally useless for operator triage.
2. **Secret/PII redaction is truncation-only, not pattern-scrubbed.** `matched_indicators` in `Finding.data` carries verbatim 120-char body snippets — JWTs, tokens, emails in error messages would be persisted unredacted.

Plus **one design gap that affects spec branches**:

3. **Framework/runtime trace matcher missing.** `framework_hints[]` is permanently empty; spec's "medium = error status + framework hint" confidence branch is unreachable.

Plus **negative-assertion test coverage** — most spec "must not" rules have no regression test (no-AI marker, no mutating methods, follow_redirects, redaction, hostname-agnosticism, RFC 7807 path). The behaviour is correct by construction today, but a regression test grid would lock it in.

## Recommended follow-ups (open before claiming stub-done)

1. **#FU-1 Evidence body excerpt + redaction.** Replace synthetic raw_excerpt with a redacted body slice (≤ 4096 bytes per spec config); add `selected_headers` + `truncation` flag to Evidence.data. Wire a regex-based secret scrubber for JWT / Bearer / API-key / email patterns before persistence. Add tests asserting redaction.
2. **#FU-2 Framework matcher.** Add `framework_hints` extraction (`signatures.py`-style table for Django/Flask/Express/Spring/Rails/...) so the spec's medium-confidence branch becomes reachable. Surfaces in `Finding.data.framework_hints`.
3. **#FU-3 Negative-assertion test grid.** One regression test per spec "must not" — no AI marker (`ai_assistance="none"` on persisted finding), no mutating HTTP methods, `follow_redirects=False`, hostname-agnostic detection, RFC 7807 path, request-ID/Server-header noise.
4. **#FU-4 Persistence completion.** Add `Finding.summary`, `first_seen_at`/`last_seen_at` update logic (depends on FU cross-run idempotence in PR #24).
5. **#FU-5 Status `rejected` emission.** Classifier returns `None` for non-flags today; spec vocabulary includes `rejected` for harmless problem-details / generic errors. Decide whether to emit `rejected` rows or keep the None contract.
6. **#FU-6 Detection-set completion.** `rest`/`v1`/`v2` probe prefixes; bare `.php:`/`.rb:` paths; Redis / ORM-exception / bare PG `ERROR:`/`FATAL:` DB signatures; `type`-with-framework-value strong indicator.
7. **#FU-7 Skip filters.** `skip_path_patterns` for mutating-intent URLs + binary content-type skip + same-origin guard (dormant until endpoint discovery, but should land alongside it).

**Stub-done blockers:** none of the follow-ups are blockers for the current MVP slice the spec asks for — but **FU-1 (Evidence excerpt + redaction)** is the one a reviewer should hit first because it affects operator-facing triage data quality. Recommend treating FU-1 as a P0 before promoting any 1.17 finding to operator review, and FU-2/FU-3 as P1 follow-ups in the next iteration.
