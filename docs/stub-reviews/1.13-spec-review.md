# Stub 1.13 (security-txt) — spec review

Audit of `backend/apps/stubs/security_txt/` against
`docs/superpowers/specs/2026-05-18-VULN-SCANNING-COOK-BOOK/01-information-gathering/13-security-txt.md`
(453-line enriched spec).

## Compliant

### Detection logic

- **Read-only HTTP.** Fetcher only calls `client.get()`. No POST/PUT/PATCH/DELETE/OPTIONS.
- **No request body.** No data/content kwarg on the GET.
- **No credentials.** Fetcher sends `Accept: text/plain, */*;q=0.1` only — no Authorization, cookies, or session headers.
- **httpx redirect handling.** `follow_redirects=True` + `max_redirects=3` per spec default. `TooManyRedirects` caught alongside `TransportError` so a misconfigured server doesn't crash the scan.
- **Cross-host redirect rejection.** Final URL origin compared to base origin via shared `_shared/url.origin` helper; mismatch → `inconclusive` so the runner never trusts an off-host security.txt body.
- **Body cap.** `FetcherConfig.max_body_bytes` default 65536 per spec §Inputs.
- **Both candidate paths probed.** Always fetches `/.well-known/security.txt` AND `/security.txt` so `conflicting_files` / `legacy_only` verdicts can fire (only 2 GETs per scan).
- **RFC 9116 §2.2 inline-comment compliance.** Parser strips inline `#` comments before the colon partition — fixed in round-1 simplify.
- **Case-insensitive field name matching** per spec §Parsing.
- **Repeated fields kept as tuples** preserving order.
- **Unknown fields preserved** with original casing; parsing continues on malformed lines.
- **Trailing-newline equality on `_bodies_differ`.** Hash normalisation before compare so a server adding `\n` to one path doesn't false-positive as conflicting.

### Validation rules

- **Contact**: scheme allowlist `{mailto, https, http, tel}`; shape-only — never dials, emails, or fetches.
- **Expires**: RFC3339/ISO-8601 timestamp parse with `Z` suffix handling; bare dates rejected.
- **Canonical**: trailing-slash-tolerant URL equality with the final fetched URL.
- **Policy / Encryption / Acknowledgments / Hiring / CSAF**: URI shape check (absolute http/https), no fetching.

### Finding rules — verdict priority

10 spec finding types covered in this priority order:

| # | Finding type | Trigger |
|---|---|---|
| 1 | blocked_security_txt | canonical=blocked |
| 2 | missing_security_txt | both absent/inconclusive |
| 3 | malformed_security_txt | present body, no parseable fields |
| 4 | security_txt_no_contact | no valid Contact |
| 5 | security_txt_expired | Expires older than now |
| 6 | security_txt_legacy_only | only legacy path served |
| 7 | security_txt_canonical_mismatch | Canonical ≠ final URL |
| 8 | security_txt_conflicting_files | bodies differ between paths |
| 9 | security_txt_missing_expires | no Expires field |
| 10 | security_txt_present_valid | everything checks |

The `legacy_only` → `canonical_mismatch` order swap (spec §Canonical legacy-placement rule) was caught by a runner test where a body served at /security.txt has Canonical → /.well-known/security.txt — that's spec-blessed legacy placement, not a mismatch.

### Persistence contract

- **Evidence.source = "path"** per shared schema; **one row per probed URL** (canonical + legacy).
- **Finding.confidence** uses cookbook vocabulary via shared `Confidence` Literal (#95).
- **Finding.status** uses `FindingStatus` enum.
- **Finding.data** carries: finding_type, http_status, primary_url, canonical_kind, legacy_kind, indicators, evidence_ids, fields (parsed contact/expires/canonical/policy/etc.), source.
- **No raw bodies persisted beyond raw_excerpt** (capped at 200 chars).

## Deferred (tracked tasks)

- **Multiple findings per scan.** Spec persistence shape allows multiple `SecurityTxtFinding` rows per scan (e.g. `expired` + `canonical_mismatch` on the same file). MVP emits only the worst-applicable verdict; secondary conditions land in `indicators`. Track if operator triage needs both rows visible.
- **`check_legacy_path` config flag.** MVP always probes both paths. The spec config option would let operators skip the legacy probe — small request-budget win, not blocking.
- **Multiple Expires values.** Spec doesn't say what to do if a file has TWO `Expires:` lines. Parser keeps both as a tuple; classifier picks `any(is_expired(v) for v in parsed.expires)` so any expired entry triggers. Defensible interpretation but not spec-pinned.
- **HTTP→HTTPS redirect preference (`prefer_https`).** MVP follows whatever the server returns; explicit upgrade logic deferred.
- **#64 body streaming.** Tracked alongside other fetchers — bound memory for hostile-large bodies.
- **`http` Contact warning.** Spec says http contact URLs should produce a warning. Current `is_valid_contact` accepts http silently; the warning would need a separate `validate_contact_with_warning(value) -> (bool, list[str])` helper. Defer.

## Summary

Stub 1.13 MVP implements the spec's deterministic core: line parser with RFC 9116 §2.2 inline-comment compliance, five pure validators, 10-finding-type priority classifier, two-path fetcher with cross-host redirect rejection + `TooManyRedirects` handling, and a runner that emits one Evidence-pair + one Finding per scan.

Spec deviations are minor — multiple-findings-per-scan, http-Contact warning, `check_legacy_path` config flag — all tracked as follow-ups, none blocking the cookbook compliance bar.

Live coverage exercised three distinct verdicts (present_valid on Juice Shop, malformed on DVWA, missing on WebGoat) — the classifier vocabulary fires correctly on real data.
