# Stub 1.8 (exposed-admin-panels) — spec review

Audit of `backend/apps/stubs/admin_panels/` against
`docs/superpowers/specs/2026-05-18-VULN-SCANNING-COOK-BOOK/01-information-gathering/08-exposed-admin-panels.md`,
applied retroactively after the operator established the
spec-review-after-stub rule (2026-05-19).

## Compliant

- **Read-only HTTP discipline.** Fetcher only calls `client.get()`; no POST/PUT/PATCH/DELETE/OPTIONS/TRACE/CONNECT. Negative assertion satisfied.
- **No AI involvement.** Detection is deterministic regex + hash compare. No LLM calls.
- **No credentials.** Fetcher passes no `Authorization` / cookies; `credentials` config field is unused in MVP per spec.
- **No hostname inference.** Candidate paths are static; detection uses response evidence only.
- **Same-origin redirect filter.** `_is_same_origin_admin_redirect` rejects cross-origin Location targets.
- **Bounded request budget.** 1 baseline + 2 nonce + 13 candidate probes per target, transport-error-isolated per probe.
- **Status filter.** 404 skipped explicitly; allowed-status responses go through evaluation.
- **Confidence vocabulary.** Only `low | medium | high` emitted (low not used in MVP — only `medium` and `high`).
- **No body persistence.** Evidence.raw_excerpt synthesizes `signal_kind: path (status N)`; the response body is not stored. Spec's "no full bodies / no cookies / no credentials" persistence rule is satisfied by virtue of not storing the body at all.

## Fixed in spec-review fixup

- **Soft-404 logic (was: any-nonce; spec: BOTH-nonces).** Spec §Soft-404 line 113-115 requires a status-200 candidate to match BOTH random missing paths before being suppressed. Previous impl built a hash set from both nonces and matched if the candidate hash was in the set — i.e., matching EITHER nonce was enough to suppress. When nonces produced different bodies (rare but possible), this over-suppressed valid candidates. Fix: when `len(nonce_hashes) != 1`, return an empty set (no reliable baseline, don't suppress anything). Regression test pinned.
- **`finding_type` field.** Spec §Persistence requires `finding_type = "exposed_admin_panel"` on every Finding. Previous impl omitted it; added to `Finding.data`. Test pinned.

## Deferred (tracked tasks)

- **#81 Finding shape spec compliance.** Spec defines `ExposedAdminPanelFinding` with `exposure_kind ∈ {admin_login, admin_dashboard, management_console, protected_admin_route, unknown_admin_surface}`, `access_state ∈ {public_200, auth_required_401, forbidden_403, redirected_same_origin, unknown}`, and `status → confirmed` for medium+ confidence. Current impl stores `signal_kind` (auth_required / body_markers / distinct_body / redirect_to_admin) and always uses `status = candidate`. Frontend has already shaped against the current Finding.data — coordinate the schema change with agent-em-frontend before landing.
- **#82 Cross-run idempotence.** Spec §Idempotence assertions: running the detector twice should update an existing Finding with `last_seen_at` rather than create a duplicate. This is a platform-wide concern (all stubs create new rows per run); requires `first_seen_at` / `last_seen_at` columns on Finding + a content-hash key for dedup. Defer until operator confirms the model migration.
- **#83 WWW-Authenticate signal + expanded body markers.** Spec §Header markers calls out `WWW-Authenticate` as a 401-vs-401-with-realm discriminator (medium confidence with sparse body vs high with body markers). Current MVP emits high for any 401/403. Spec §Management-console markers also lists ~20 entries (phpmyadmin, pgadmin, grafana, kibana, jenkins, sonarqube, prometheus, etc.) — current impl has 6. Both improve precision but MVP heuristic is acceptable on real auth-gated admin routes.
