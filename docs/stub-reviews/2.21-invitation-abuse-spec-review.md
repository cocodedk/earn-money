# Stub 2.21 (invitation-abuse) — spec review

Audit of `backend/apps/stubs/invitation_abuse/` against
`docs/superpowers/specs/2026-05-18-VULN-SCANNING-COOK-BOOK/02-authentication/21-invitation-abuse.md`.

## Compliant

- **Gate discipline.** Three gates checked in order: `allow_registration_probes` RoE knob →
  `authorized_test_accounts` → `FIXTURE_INVITATION_TOKEN` env var. Each emits a typed
  `AUTH_PROBE_REFUSED` or `FIXTURE_REQUIRED` event on failure.
- **No mutations in passive mode.** Runner only performs mutations when the RoE knob is on.
  `test_gates.py` covers all three refusal paths.
- **No AI.** Detection is deterministic keyword/signal matching only.
- **Bounded probes.** Three probes per run: surface GET, preview GET, accept POST. No loops, no
  guessing, no brute force.
- **Transport-error isolation.** Each `submit_probe` returns `None` on failure; runner emits
  refusal event and stops cleanly. Covered by three transport-error runner tests.
- **Confidence vocabulary.** Only `low | medium | high` via shared `Confidence` type alias.
- **Status vocabulary.** Only `candidate | confirmed` emitted; `high` confidence on acceptance.
- **Body-signal matching.** `classify_wrong_recipient` and `classify_reuse` share
  `_classify_accept_signal` — identical accept-signal set (`_ACCEPT_SIGNALS`) for both.
- **No hostname inference.** Classifier reads response text and status codes only.
- **Preview exposure detection.** Unauthenticated GET leaking `workspace`/`role`/`invited_by`
  fields classified as `sensitive_invite_preview`, `candidate`, `medium`. Covered by
  `test_classify_discovery.py`.
- **Wrong-recipient detection.** Confirmed high-confidence when unrelated session accepts.
  Covered by `test_classify_mutations.py` and `test_runner.py`.
- **Invite-surface classification.** `classify_invite_surface` correctly gates on path-hints
  AND body keywords. Covered by `test_classify_discovery.py`.

## Deferred (follow-up tasks)

- **`classify_reuse` and `classify_role_escalation` not integrated into runner.**
  Both functions are implemented, tested, and classified correctly but the runner only runs
  the wrong-recipient probe. Reuse and role-escalation probes require the fixture to support
  a "use token once, then reuse" and "accept with elevated role" scenario. Deferred to a
  fixture-extension PR.

- **Full `InvitationAbuseFinding` schema.** Spec defines `weakness`, `affected_scope`,
  `impact_summary`, `reproduction_summary`, `pii_redacted`, `remediation`, `signature_ids`,
  `evidence_ids`. MVP `Finding.data` stores `kind`, `endpoint`, `method`,
  `requires_manual_review`. Field-shape compliance is platform-wide (#81 analogue) — defer to
  the same workstream as other Phase-2 stubs.

- **`InvitationAbuseSignature` and token metadata.** Spec requires token length, location,
  character-class fields. Not persisted in MVP. Deferred with full schema above.

- **Config knobs** (`scan_mode`, `allow_mutating_invite_probe`, `max_invite_create_attempts`,
  `max_accept_attempts_per_invite`, `allowed_invite_domains`). MVP gates on
  `allow_registration_probes` + `authorized_test_accounts` which covers the mandatory safety
  gate. Fine-grained knobs deferred.

- **Invite creation probe (Phase 4).** Spec §4 "controlled invite creation probe" is not
  implemented. Requires `allow_mutating_invite_probe=true` knob and invite-creation fixture
  endpoint. Deferred.

- **CSRF handling.** Spec §Acceptance "handles CSRF failures gracefully" — runner sends JSON
  bodies; CSRF friction only matters for form-based targets. Deferred.

- **`stale` finding path.** No code path produces `status=stale`. Deferred to platform-wide
  cross-run dedup workstream.
